## P1 — критические ошибки

### 1. Четыре страницы показывают PHP Parse error, но отвечают HTTP 200

**Статус: исправлено на тестовой копии 21.08.2026.** Ниже сохранено исходное наблюдение аудита для истории и проверки программистом.

- `/publications-teg/peregorodki`;
- `/publications-teg/poly`;

Ответ содержит:

`Parse error: syntax error, unexpected '?' in .../sites/all/themes/kronotek/views-view-table--all-stt--block.tpl.php on line 50`

**Почему опасно:** пользователь видит ошибку, а поисковик получает код успешной страницы. Ошибка не попадает в обычный отчёт 404 и может долго оставаться незамеченной.

**Задача программисту:** проверить строку 50 шаблона, совместимость синтаксиса с PHP тестового сервера, затем добиться обычного HTML 200. Для необработанных исключений сервер должен возвращать 5xx, а не 200.

- прямые ссылки на `kronotech.ru` найдены на 445 из 449 HTML-страниц: 3 684 вхождения, 83 уникальных адреса;

  - `/mokryy-fasad`;

Для автоматических аудитов такие переходы нужно только маркировать как внешние переходы на прод, чтобы не смешивать результаты двух серверов. Переписывать sitemap на Hostland не требуется.

## P2 — SEO и техническая целостность

### 4. Canonical отсутствует на всех HTML-страницах

`link rel="canonical"` не найден ни на одной из 449 HTML-страниц.

Для тестовой копии рекомендован безопасный принцип:

- рабочие копии материалов — canonical на соответствующий HTTPS URL `kronotech.ru`;
- боевой сайт — self-canonical на чистый URL без служебных GET-параметров;
- служебные и тестовые URL — `noindex` и исключение из sitemap.

Canonical нельзя добавлять массовой строковой заменой без таблицы соответствий: часть старых адресов редиректит на другие страницы.

### 5. Состав sitemap требует отдельного решения, домен указан правильно

В sitemap находятся `/node/1130`, `/tests4`, `/genpodryad`, `/yandex_auth/oauth`, `/search`, `/home`, `/en`. Хост боевого сайта указан намеренно и правильно. Вопрос только в том, должны ли перечисленные служебные URL индексироваться; это проверяется по каждому типу отдельно, без изменения домена sitemap.

Текущий `robots.txt` тестовой копии:

```text
User-agent: *
Disallow: /
```

Для теста это правильно: копия закрыта от обхода. Убирать запрет до переноса нельзя. Sitemap с рабочими URL `kronotech.ru` сохраняется.

### 6. Смешанный HTTP/HTTPS-контент на 407 страницах

Найдено 9 152 вхождения HTTP-ресурсов, 1 007 уникальных адресов:

- 869 JPG;
- 79 JPEG;
- 49 PNG;
- 5 WebP;
- 5 MP4.

Браузер часть адресов автоматически переводит на HTTPS, поэтому визуально ошибка может быть незаметна. Однако это лишние редиректы, риск блокировки ресурсов и источник разных URL одного файла.

**Задача программисту:** исправить базовую схему генерации Drupal image styles и абсолютных файловых URL, затем точечно обновить сохранённый HTML. Не ограничиваться заменой в CSS.

### 7. Авторская микроразметка не покрывает большинство статей

На сайте найдено 253 страницы с `BlogPosting`. Только две из них содержат сущность `Person` в JSON-LD. На остальных 251 статья не связана с человеком-автором в структурированных данных.

**Задача программисту:** после проверки реального назначения авторов выводить в `BlogPosting.author` объект `Person` с именем и HTTPS URL профиля. Профиль автора должен быть видим пользователю и содержать проверяемые сведения о компетенции. Нельзя создавать вымышленных экспертов.

### 8. Изображения: alt, размеры и lazy loading

По 31 650 вхождениям изображений:

- 15 849 без `alt`;
- 22 859 без `width`/`height` или эквивалентного резервирования места;
- 16 571 используют lazy loading;
- 445 страниц содержат хотя бы одно изображение без `alt`;
- 445 страниц содержат изображения без явных размеров;
- на 20 страницах есть изображения, но нет ни одного lazy-изображения.

**Правило:** содержательным изображениям — осмысленный `alt`; декоративным — `alt=""`; для изображений ниже первого экрана — lazy; для LCP-изображения первого экрана lazy не ставить; размеры или `aspect-ratio` задавать заранее.

### 9. Дополнительные SEO-ошибки

- `og:description` отсутствует на 100 страницах;
- четыре страницы PHP-ошибок не имеют title, description и H1;
- 10 страниц без meta description, включая служебные;
- два H1 на `/stroitelnye-raboty` и `/privacy-policy`;
- `lang` и viewport отсутствуют на четырёх сломанных страницах;
- профиль `/authors/vyacheslav-erokhin` закрыт `noindex`, поэтому его вклад в E-E-A-T для поиска ограничен;
- HTTPS `www.lazernaya-rezka-piter.ru` отвечает 200 как отдельное зеркало, а canonical отсутствует;
- URL с завершающим слешем сначала выдаёт Location с `http://`, хотя в итоге открывается HTTPS.

Количество форм не считается ошибкой: они специально разделены по сценариям. Исправить нужно только повторяющиеся HTML-ID, чтобы JavaScript, аналитика, подписи и автозаполнение однозначно работали с каждой формой. Формы не отправлялись во время аудита.

Шесть основных горизонтальных разделов являются структурой сайта — их не нужно ломать. Оптимизировать следует верхний служебный слой и дублирующие CTA.

6. Не включать намеренно отсутствующие видео в список дефектов тестового переноса.
7. Исправить шаблоны изображений и зарезервировать размеры.
8. Устранить дубли ID, сохранив раздельные формы, и провести отдельный тест отправки каждой формы в Bitrix24.
9. Проверить JSON-LD статей, проектов, услуг, автора, контактов и хлебных крошек.
10. После повторного аудита переносить изменения на прод только отдельными проверяемыми пакетами.

## Что не делать

- не убирать `Disallow: /` с тестовой копии до завершения миграции;
- не ставить всем страницам один canonical на главную;
- не переносить тестовые абсолютные URL на боевой сайт;
- не делать 301 для каждой 404 без смыслового аналога и данных о посещениях;
- не применять глобальные CSS-селекторы к `.row`, `.col-*`, `a` или меню ради исправления одной страницы;
- не очищать или перезаписывать БД ради диагностического аудита;
- не считать ответы 509 битым URL: во время массовой проверки Hostland ограничил частоту запросов. Эти адреса требуют повторного медленного контроля, а не редиректа.

2. Кто отвечает за повторную приёмку после каждого пакета: программист, маркетолог или оба по чек-листу?

Уже согласовано: sitemap теста содержит URL `kronotech.ru`; видео не переносятся из-за объёма; формы разделены по сценариям; хлебные крошки прокручиваются горизонтально.

## Ограничения аудита

- формы не отправлялись и внешние сообщения не создавались;
- функциональность личного кабинета и платёжных сценариев отсутствует в области проверки;

- 183 ответа 509 в дополнительной выборке являются серверным rate limit, а не подтверждёнными битыми ссылками;
- прямой PageSpeed API вернул 429, поэтому результат получен через официальный интерфейс PageSpeed Insights и сохранён отдельно;
- весь аудит выполнялся на `lazernaya-rezka-piter.ru`; боевой `kronotech.ru` не изменялся.

## 📚 Зачем

Комплексный аудит нужен не для количества найденных ошибок, а для правильного порядка исправлений. Сначала устраняются ошибки, которые ломают страницу или смешивают тест и прод. Затем исправляются шаблонные SEO-проблемы. И только после этого имеет смысл полировать отдельные отступы: иначе косметическая работа будет повторяться после каждого системного изменения.
